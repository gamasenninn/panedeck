# 別マシンから受付ペインを起こす

PaneDeck が、メッセージを受けるサーバとは**別の機械**にあるときの仕組み。

**変わるのは「ファイルに載るまで」だけ。** 載った後は同じ機械のときと完全に同じ。

> **この文書の立場**: 設計の説明。**本番のサーバへ別マシンから繋いだ検証は
> まだ済んでいない**（2026-10-05 時点）。確かめたのは形 —— 自前で立てた
> HTTP の流れで ①〜⑤ が通ること、切断したらサービスが落ちて起こし直され
> ることまで。何が未確認かは末尾にまとめてある。

## 全体の流れ

```
【A 機: メッセージのサーバ】                 【B 機: PaneDeck】

人が投稿
  @cc-panedeck 見てほしい
      │
      ▼
 サーバが受ける
      │
      ▼
 queue ファイルに 1 行追記   ①
      │
      │ ②  HTTP で流す（NDJSON）
      │    GET /…/stream?project=…&since=<最後の id>
      └──────────────────────────────▶ サービス（#29）が
                                        接続を抱え続ける
                                             │
                                             ▼ ③
                                     ローカルのファイルへ 1 行追記
                                             │
                                             ▼ ④
                                     トリガー（#28）が 300ms ごとに見る
                                             │
                                             ▼ ⑤
                                     受付ペインが「指示待ち」なら
                                     打ち込む → 500ms → Enter
                                             │
                                             ▼ ⑥
                                     受付が自分で queue を読み、返信
```

**同じ機械なら ② と ③ が無く、① で書かれたファイルを ④ が直接見る。**

## 設定はこの 2 つだけ

PaneDeck 側に足すコードは無い。

```json
{
  "services": [
    { "name": "受信", "command": "<HTTP の流れを抱えてファイルへ書くコマンド>" }
  ],
  "triggers": [
    {
      "watch": "<そのコマンドが書くファイル>",
      "pane": { "title": "受付" },
      "send": "新着 {count} 件（最新 id={id}）。queue を読んで対応して。"
    }
  ]
}
```

## ② 流れてくるのは便だけではない

| 流れてくるもの | 意味 | クライアントのすべきこと |
|---|---|---|
| `{"id":…}` | **本物の便** | ファイルへ書く |
| `{"__hb":…}` | 心拍（十数秒ごと） | **捨てる。** 書くと心拍ごとに起こされる |
| `{"__bye":{…}}` | **予告された切断**（デプロイ・寿命） | 捨てる。驚かなくてよいと分かる |
| JSON でない文字列 | proxy のエラー本文など | **書かない。** 書くと `since` の計算が壊れる |

★ **`__` で始まる行は全部捨てる**（許可方式で `{"id"` だけを書く）。`__hb` だけを
名指しで捨てると、サーバが新しい制御行を足した日に**全部が「便」として
流れ込む**。

★ **切断は正常。** サーバは数十分ごとに意図して閉じ、再ログインと再認可を促す
（部屋のメンバーかどうかは接続ごとに見直される）。切れたこと自体は異常ではない。

## ③ なぜファイルを挟むのか

**ここが設計の核。**

HTTP の流れを PaneDeck が**自分の中で**持つと:

```
便を受け取った → ペインへ伝える前に落ちた → 便は消える
```

ファイルを挟むと:

```
便を受け取った → ファイルに載っている → 落ちても残る
  → 次の起動で、どこまで届けたかの記録から続きが届く
```

**「受け取った」と「伝えた」の間に落ちても失われない**ための 1 枚。だから
**HTTP を PaneDeck に組み込まない** —— 組み込んでも結局ファイルへ書くことに
なり、#29 を内側に作り直すだけになる。

加えて、組み込めば PaneDeck がトークンを抱え、サーバの作法（心拍・切断の予告・
`since`）を知ることになる。**プロトコルはサーバ側、生かし続けるのと配るのは
PaneDeck** という分担にしておけば、どちらも相手の事情を知らずに済む。

## ④〜⑤ ここから先は同じ機械のときと同一

- **300ms ごとに大きさを見る。** 変わっていなければ読まない（#35）
- 送るのは**ペインが `指示待ち` のときだけ**（#27）。作業中・確認待ちには
  割り込まず、溜めて**区切りで 1 通にまとめて**送る（10 件来ても 10 回
  起こされない）
- **打つのと Enter は別の出来事**として送る（一度に送ると貼り付けと見なされ、
  文面が入力欄に残って実行されない。#32）
- **ペインが動いたのを見てから**「届いた」とする。動かなければ押し直し、
  それでも駄目なら保留へ戻す

## 位置を数える印は 3 つある

混ざると「二重に届く」か「黙って飛ばす」になる。

| 印 | 意味 | どこに |
|---|---|---|
| **受信カーソル**（`since`） | どこまで**受け取った**か | B 機のファイルの最後の id |
| **配達カーソル** | どこまで**ペインに伝えた**か | PaneDeck の設定（`triggerCursors`） |
| **処理済み**（watermark） | どこまで**扱い終えた**か | サーバ側の作法に従うファイル |

**なぜ 3 つ要るか**: 切断中に来た便は拾いたい（受信）。でも「受け取ったが返事を
保留中」の便を再提示されたくない（処理済み）。ペインに伝えたかどうかは、
エージェントが扱い終えたかとは別（配達）。

★ **1 つのファイルに配る人は 1 人。** 配達カーソルは監視パスを鍵に保存される
ので、同じファイルを 2 つのトリガーが見ると互いに潰し合う。設定でも
重複を落とすようにしてある。

## ⑥ ペインに渡るのは識別子だけ

```
新着 2 件（最新 id=7154224d-…）。queue を読んで対応して。
```

**本文は渡さない。** 打ち込まれた文字は**人が打ったのと同じ扱い**で
エージェントに届くので、誰かが書いた本文をそのまま流すと、**その人が
user としてエージェントへ指示できる**ことになる。中身は受け手が自分の道具で
取りに行く。

PaneDeck は差し込む値から改行と制御文字を落とすが、**それ以上はできない**。

## 壊れたとき、どこで気づくか

**層ごとに別の症状が出る。**

| 壊れた場所 | 見える場所 |
|---|---|
| HTTP が繋がらない | サービスが落ちて起こし直され、**ツールバーに「再起動中 1・計 7 回」** |
| ファイルが読めない | ツールバーに **「ファイルを読めません」** |
| 題のペインが無い | ツールバーに **「ペインがありません: 受付」** |
| 同じ題が 2 枚ある | ツールバーに **「同じ題のペインが 2 あります」**（手当たり次第には送らない） |
| ペインが作業中 | ペインに **「保留 3」** |
| 打ったが実行されない | ツールバーに **「実行されませんでした。入力欄を片付けてください」** |

## HTTP が持ち込む唯一の新しい故障

**繋がっていないのにプロセスは生きている**状態。

```
サービスは走っている → 再起動回数は 0
便は来ない           → 「静かな日」と見分けが付かない
```

ローカルのファイルは「切断」しないので、これは HTTP だけの問題。

**答え: クライアントに粘らせず、落とす。** N 回続けて繋がらなければ `exit` し、
#29 の再起動（1,2,5,15,30,60 秒）と回数の表示に任せる。実測:

```
切る前           client 1 本
8 秒後           0 本   ← 続けて失敗して終了
16 秒後          1 本   ← #29 が起こし直した
24→32 秒         0→1 本 ← 待ち時間が延びていく
復帰後 60 秒     1 本   ← 繋がり、便も届いた
```

★ CC のセッションが単体で待ち受けるときは**自力で粘るのが正しい**
（supervisor が居ないので）。**PaneDeck の中では前提が変わる。**

## 認証

B 機のサービスがサーバへログインしてトークンを取り、使い回す（401 のときだけ
取り直す）。資格情報は B 機に置く。

**PaneDeck はトークンを見ない。** 知っているのは「このコマンドを走らせ続けろ」
だけ。設定は平文の JSON で UI も読むので、秘密を置かない形にしてある。

## そもそも何のための HTTP か

**便利さではなく隔離。** 本番の DB・メディア・秘密鍵がある機械と、AI が動く
機械を分けられる。同じ機械なら HTTP は要らない（ファイルを直接見ればよい）。

## 未確認のこと

- **本番のサーバへ別マシンから繋いでいない。** 検証した機械には資格情報が無く、
  1 台しかなかった
- **連続配達を実物のエージェントで見ていない。** 試験台ではペインを
  「指示待ち」に偽装していたが、1 通目が届いた瞬間にシェルの出力でその偽装が
  崩れ、以後は保留止まりになった（**製品としては正しい動作**）
- サービスの「粘らず落ちる」挙動は自前のクライアントで確かめたもの。
  既存のクライアントにその選択肢があるかは、サーバ側の判断
