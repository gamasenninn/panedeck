## 設計の要点（なぜそうしたか）

### ロジックを lib/ に隔離した

`lib/` は **Electron にも node-pty にも依存していない**。pty 生成関数・現在時刻・
設定やログの保存先パスを、すべて**依存性注入**で受け取る。

おかげで単体テスト 275 件が Electron 起動なしで 2 秒弱で回り、「出力が止まって
400ms 経つと待機になる」といった時間依存の遷移も実時間に頼らず検証できる。

新機能はまず `lib/` に純粋なロジックとして書き、`main.ts` の IPC で繋ぐ順序を守ること。

### 状態も並び順もメインプロセスが持つ

レンダラは 300ms ごとに `session:list` を取って画面と突き合わせる（`sync()`）。
**この構造では、レンダラ側に真実を持たせると必ず巻き戻る。**

- 並び順は `SessionManager.reorder()` が持つ。レンダラが持つと、ポーリングのたびに
  突き合わせが要り、書き損なうと並びが戻る
- 一斉入力の状態フィルタもメイン側で判定する。レンダラの状態は最大 300ms 古い

### E2E は実ユーザーの環境を触らない

`launchApp()` は設定パスを渡さなければ**使い捨ての一時ディレクトリ**を使う。
渡さないと実 userData を読み書きしてしまい、テストがユーザーの設定に従って動き、
ユーザーのフォルダにテスト用のログを書き散らす（実際に起きた）。

### 実プロセスを使うテスト

`real-pty.spec.ts` と `auto-restore.spec.ts` はフェイクを使わない。前者は pty 連携
そのもの、後者は**起動時の復元がフェイクを差し込む前に走る**ため。
`tests/packaged/` は生成物を起動して、パッケージ版だけで壊れる経路を見る。

## ハマりどころ（再発しやすい）

### 制御文字は必ず `\x1b` のように書く

`status-detector.ts` の `ANSI_PATTERN` には**生の ESC バイトが直接埋まっていた**。
ソース上で不可視なので、TS 化で書き写したときに落ちた。ESC が無いとパターンが
ただの `[` に一致し、プロンプトの `[Y/n]` を ANSI と誤認して削っていた。

### ANSI の除去は取りこぼすと判定が丸ごと死ぬ

この一連で 4 つ直した。**どれも特定のエージェントの話ではなく、全体の入力待ち
判定を壊していた。**

| 欠陥 | 影響 |
|---|---|
| OSC に終端が無い | 最初の OSC 以降を末尾まで削除（実ログで 4405 文字 → 46 文字） |
| 行数の窓が空行を数える | 全画面 TUI は画面下を空行で埋めるので中身が窓の外へ出る |
| 宙に浮いた ST が残る | 末尾 2000 文字の境界が OSC の途中に落ちたとき |
| CSI の中間バイト非対応 | `ESC [ 0 SP q` が本文に残る |

**シェルはプロンプトのたびにタイトル設定の OSC を出す**（PowerShell も）。
1 つ目は事実上すべてのエージェントで判定を殺していた。

### 状態を見ない pty 操作は落ちる

`resize()` は終了済みセッションを弾く必要がある。node-pty は終了した pty の
リサイズで例外を投げ、レンダラは文字サイズ・列数・ウィンドウの変化のたびに
全ペインへ resize を投げるので、**終了したペインが 1 つ残っているだけで
メインプロセスの未処理例外**になる。`write()` と同じ扱いにそろえてある。

### 消えたプロセスをリサイズするとアプリごと固まる（#16）

例外で済まないほうの話。**ConPTY は子プロセスが消えた後にリサイズすると
戻ってこない。** node-pty の `resize()` はメインプロセスの上で同期的に走るので、
戻らなければアプリ全体が止まる。ペインは出ず、画面も IPC も無応答になる。

`exited` フラグだけでは足りない。**node-pty の `onExit` は実際の終了より遅れて
届く**ので、「もう居ないのに `exited` はまだ false」という隙間で踏む。
`SessionManager.resize()` は `pty.pid` に**シグナル 0 を送って生死を確かめる**
（`isProcessAlive` として注入可能）。

診断でこれだけ遠回りした。同じ轍を踏まないための道しるべ:

- **`page.evaluate` も `electronApp.evaluate` も固まる**ので、レンダラが原因に
  見える。どちらも同じ経路を通るだけで、切り分けの材料にならない
- Playwright を通さずに測ること。**main から `process.stdout.write()` させ、
  `electronApp.process().stdout` を読む**。心拍で main のループの生死が分かる
- レンダラの生死は `session:list` の到着で分かる（300ms ポーリングが届く）
- **main にタイマーを 1 つ置くと再現しなくなる**ことがある。観測が結果を変える
  ので、instrumentation は疑ってかかること
- 短命なプロセスでしか出ない。長く生きるプロセスだと踏まない
- **`npm run test:e2e` はビルドしない。** `dist/` が古いまま「直っていない」と
  判断しかけた。レンダラを触ったら `npm run build` を挟むこと

`renderer.ts` 側では resize 要求を 150ms まとめてから送る（`requestPtyResize`）。
ペイン生成直後はレイアウトが 2 段階で確定し 80x24 → 79x24 → 実寸と続けて
飛ぶため。**これは緩和であって修正ではない**（待ち時間を 1 秒にしても踏んだ）。
効いているのは pid の生存確認のほう。

### xterm の癖（3 つとも実際に時間を溶かした）

- **空行でも `hasSelection()` は true、`getSelection()` は空文字列。**
  端末の中央をクリックすると空行に当たる
- **`.xterm-rows` はポインタイベントを受けない。**行の div はクリックできず、
  Playwright は操作可能になるのを待ち続けてタイムアウトする。選択は
  `.xterm-screen` に座標指定で行う
- **`attachCustomKeyEventHandler` が `false` を返しても、ブラウザ既定の動作は残る。**
  隠しテキストエリアに文字が入り二重に送られる。`preventDefault()` が要る

### 隠れているペインは測らない

`fit()` はレイアウトを持たないペインを飛ばす。測ると 0 桁になり、その値で pty を
リサイズしてしまう。1 ペイン拡大でも並べ替えでも通る経路。

### レンダラは ES モジュール（相対 import に `.js` が要る）

バンドラを挟んでいないので、`./renderer/keys.js` のように**拡張子まで書く**
（`.ts` ではない）。npm の bare import は解決できないため、xterm は script タグで
読み込んだグローバルを使う。

かつて「レンダラで `const deck` と宣言するとスクリプト全体が落ちる」という地雷が
あったが、**モジュール化で解消した**（トップレベルの名前がモジュールに閉じるため）。
`const api = window.deck` はそのままだが、もう別名にする必然性は無い。

### テストのリセット直後はペインがまだ残っている

`resetSessions(electronApp, page)` は page を渡すとペインが 0 になるまで待つ。
渡さないと**前のテストの残骸ペインで即座に成立**する。**必ず page を渡すこと。**

### ネイティブダイアログはテストを止める

`window.alert` / `confirm` はレンダラをブロックし E2E が復帰不能になる。
通知は `showMessage()` へ。

### PowerShell から git commit するとき

`-m` にヒアストリングを渡すと、中の引用符や `--` で引数が壊れる（2 回踏んだ）。
**メッセージはファイルに書いて `git commit -F` を使うこと。**

## 調査の道具

### `scripts/inspect-log.mjs`

保存したセッションログを、**判定が実際に見る形**（末尾 2000 文字 → ANSI 除去 →
空行を除いた末尾 10 行）で表示し、プロファイルごとの判定結果も出す。

```bash
npm run build
node scripts/inspect-log.mjs logs/codex.log
```

**判定ロジックは再実装せず、ビルド済みの本体を呼んでいる。**一度写して持った結果、
本体を直してもスクリプトが古いままで「直したのに直らない」と誤認した。

エージェントを足すときの手順:

1. そのエージェントを PaneDeck で走らせ、入力待ちで止める
2. ペインの **ログ** ボタンで保存（生の出力が要るので `logStripAnsi` は false 推奨）
3. このスクリプトに掛けて、判定が見る文字列を確認してからパターンを起こす

**実機で確かめたものだけを足すこと。**当て推量の正規表現は「実行中を入力待ちと
見なす」方向に倒れ、誤検知は取りこぼしより悪い。

### `npm run test:packaged`

`npm run pack` の生成物を起動し、asar からの読み込み・ESM の解決・node-pty の
読み込み・設定の読み書きを確認する。パッケージ版だけで壊れる経路を見るためのもの。

### エージェントの画面を採取する手順（#27）

状態判定のパターンは**実機から採る**。採り方そのものに落とし穴があるので残す。

`scripts/` には置いていない（一度きりの調査で、置くと古くなる）。やり方:

1. **空の作業フォルダ**を作る。他リポジトリの内容が写り込まないため
2. PaneDeck を実 pty で起動し（`useFakePty` を呼ばない）、そのフォルダで

3. `SessionManager.getLog()` を段階ごとに保存する。**判定が見るのと同じ文字列**

4. 権限の確認は**必ず Esc で断る**

**`claude` には `--permission-mode default` が要る。** これを付けないと、
入れ子で起動した Claude Code が親の auto mode を継承し、**確認を出さずに
自動承認する**。「必ず断る」という手当ては、確認が出て初めて働く。実際に
1 回目の採取でファイルが書かれた（空フォルダ内だったので実害は無かった）。

採取したサンプルをテストへ固定するときは、**パス・ユーザー名・作業内容を

### 採取で分かった、机上では間違える点（#27）

- **`❯` は Claude Code の入力プロンプト**であって選択肢の印ではない。既存の
  パターン一覧から机上で分類すると逆になる

- **`Esc to cancel` を質問の印に使ってはいけない。** 断った後も判定の窓に残り、

### 判定は「画面」ではなく「記録の末尾」を見ている（#31）

**この制約を知らずに状態判定を触ると、必ず回り道をする。**

判定が読むのは pty が吐いたバイト列の末尾 2000 文字。これは**塗られたものすべての記録**であって、画面そのものではない。全画面 TUI は変えた領域だけを塗り直すので、**記録の末尾は「最後に塗られた場所」**になる。画面には見えているのに窓に入らない、が普通に起きる。

実測（#28 の dogfood、一仕事を終えた Claude Code のペイン）:

```
ANSI 除去後のログ全体        19,114 文字
判定が見る窓                  2,000 文字
"mode on"（入力欄の印）    末尾から 16,843 文字手前
```

画面には入力欄もフッターも出ていたが、窓には影も無い。ペインは `入力待ち`（判別不可）に落ち、#28 のトリガーは配達せず保留し続けた。

**窓を広げても直らない。** たまたま入る状況が増えるだけで、入らない状況は必ず残る。窓が狭いのではなく、見ている対象が違う。

なお同じ窓は ANSI 除去後に**実質 1 行**だった。Claude Code は改行ではなくカーソル移動で描くので、「末尾 10 行」も数える対象を持たない。

dogfood 初期に報告された「スクロールするとバッジが点滅する」も同じ原因の裏返し。スクロールが再描画を起こし、その再描画が記録の末尾になる。

**直すなら、メインプロセスでもバイト列を端末エミュレータへ食わせ、描画後の画面を読む**（#31）。

## 裏で走らせ続けるコマンド（#29）

### 出力をペインへ流さない —— これは制約ではなく設計

コマンドの仕事はファイルへ書くことで、ペインへ伝えるのは**ファイルを見ている
トリガー（#28）**。間にファイルを挟んでいるから、受け取ってから伝えるまでに
PaneDeck が止まっても行は残る。**直接流していたら、まさにその行が失われる。**

ログは見られるが、それは**人が見るため**。エージェントを起こす経路ではない。

### Windows では「子が残る」のが既定

`child.kill()` は**起動したプロセスだけ**を終わらせる。`shell: true` で起こして
いる以上、その先の node は生き残る。`lib/spawn-service.ts` が `taskkill /T` で
プロセスツリーごと落としているのはこのため（他の OS ではプロセスグループへ
シグナル）。

**E2E に「閉じたら子プロセスを残さない」がある。** 実プロセスを起こし、pid を
ファイルに書かせ、アプリを閉じてから `process.kill(pid, 0)` で消えるまで待つ。
フェイクでは確かめられない部分なので、ここだけは実プロセスを使う。

### 起こし直しはタイマーではなく `tick()`

`ServiceRunner` は時刻を注入で受け取り、`tick()` で「起こし直す時刻を過ぎたか」
を判断する。**時計を差し替えるだけで決定的に試せる** —— バックオフの検証に
実時間を待たない。main が 1 秒ごとに `tick()` を呼ぶ。

30 秒走れたサービスは「働けた」とみなして失敗の数を忘れる。一度安定した後の
1 回の終了で、待ちが最大のままになるのを避けるため。

### `restart` の打ち間違いは `always` に寄せる

`never` だけを受け付け、それ以外は `always`。**打ち間違いを「起こし直さない」と
解釈すると、落ちたまま黙って止まる。**

### また heredoc で逆スラッシュが潰れた

`tests/e2e/service.spec.ts` を `cat > ... <<'EOF'` で書いたとき、テンプレート
リテラルに埋めた**二重の逆スラッシュ + n** が**一重**に潰れた。TS のテンプレート
リテラルとしては改行のエスケープになるので、**生成した node スクリプトの
文字列リテラルに本物の改行が入り、構文エラー**になった。E2E 5 件が落ち、
原因を cmd の引用符の扱いだと誤って書きかけた。

**この節を書くときも同じことが起きた。** 上の段落を heredoc で書いたら、
説明に使った逆スラッシュまで潰れて「`\n` が `\n` に潰れ」という無意味な文に
なった。**だから逆スラッシュは文章でも書かず、言葉で言う。**

- **cmd は無関係だった。** `\"` は正しく通っていた
- 直し方は 2 つ重ねた: エスケープに敏感なファイルは **Write で書く**、
  そして**テスト用スクリプトに改行文字を使わない**（1 文字書き足して
  文字数で数える）
- `npx playwright test` は**ビルドしない**。これも今回また踏んだ

## 打つことと、確定することは別の出来事（#28 の dogfood）

**文面と確定の CR を一度に書いてはいけない。** Claude Code は塊で届いた入力を
貼り付けと見て、末尾の CR を**改行として入れる**。文面は入力欄に残り、実行されない。

実測（文面 91 文字・同じ構成・変えたのは PaneDeck 側だけ）:

| 送り方 | 長い文面 91 文字 | 短い文面 17 文字 |
|---|---|---|
| 一度に書く | **0 / 4** | 5 / 5 |
| 分けて書く（500ms） | **4 / 4** → 製品実装で 5 / 5 | — |

**手で使っている限り出ない。** 人は「文字を入れる」「Enter を押す」を別々に
やっている。一度に送っていたのはトリガーだけ。

- `SUBMIT_DELAY_MS` を縮めるときは**必ず実機で測り直すこと**。失敗しても
  「打てている」ので、E2E でも単体でも緑のまま通る
- ペインごとの送信 API（`api.input`）に替えても直らない。**同じ
  `sessionManager.write()` に行き着く。** 効くのは経路ではなく**間隔**

### 送っただけでは届いたと言わない

以前は書いた時点でカーソルを進めていた。実行されなければ**行は消費され、
文面は入力欄に残り、何も起きない** —— この機能が取り除こうとした
「黙って何もしない」そのものだった。

いまは `TriggerWatcher` が手順を持つ: 打つ → (500ms) 確定 → ペインが
指示待ちから動いたら確認。動かなければ押し直し（最大 3 回）、それでも
動かなければ**保留へ戻して**ツールバーに出す。

- 諦めた後は、ペインが動くまで打ち直さない。**入力欄に文面が残っている**ので、
  重ねて打つと繋がって意味をなさなくなる
- 押し直しは **CR だけ**。文面を打ち直さないので、確認を取り違えても
  二重に送ることはない（空行が 1 つ入るだけ）

### トリガーが届くのは claude のペインだけ

送る条件は `指示待ち`（#27）。**シェルのプロファイルはこれを名乗れない**
（#30 で記号による判定をやめ、素のプロンプトは `待機` になった）。
シェルのペインへトリガーで送ることはできない。

## 郵便受けの歯止め（#34 の合意、2026-10-08）

本体と受付が**郵便受けだけで 3 往復**して決めた（#34 のコメントに全文）。
入れたもの:

- **① ② ③ 配達の上限**（`limit`）。トリガーごと・配達で数える。当たったら
  **保留して捨てない**。**人が「配達を再開」を押すまで戻さない**

### 決めるときに効いた実測

- **10/7 の Tealus は 15:49 からの 10 分で 6 回**。小野さんの普通の会話が
  そのまま「10 分に 6 回」の縁にいた → **Tealus には掛けない**
- 本体と受付の 1 往復は約 54 秒 → 暴走すると 1 つの郵便受けに 10 分で約 11 回。
  正当な連投は 2〜3 通。**6 なら隙間に収まる**

### 実装で踏んだこと

- **watcher が `TriggerConfig` / `TriggerState` を自前で二重に持っていた。**
  `types/panedeck.d.ts` にだけ `limit` を足したら型検査で落ちた。いまは
  型の置き場から読み込んでいる（CLAUDE.md の「1 つだけ」）
- **止めている理由が、ペインが作業中の回だけ消えていた。** 「指示待ちで
  なければ打たない」の早期 return が先にあったため。止めている判定を先に見る
- ★ **古いデッキは設定を書き戻すときに知らない項目を捨てる**
  （`updateSettings` は読み直して正規化してから書く）。新しい項目を実設定に
  入れたら、**古いデッキが次にカーソルを保存した時点で消える**。
  **設定に足すのは、新しいビルドで再起動する直前**
- E2E で「作業中」を出した直後に「指示待ち」へ戻すと、**300ms の見回りが
  作業中を一度も見ない**。確認が済む（保留 0）のを待ってから戻す

### 閉じるたびに偽の「ペインがありません」が残っていた

閉じる処理がペインを先に畳み、プロセスが消えるまでの間にトリガーの見回りが
走って記録していた。**10/6・10/8 の再起動で毎回出ていた。** いまは
`stopTriggers()` を**ペインを畳む前に**呼ぶ。

★ **E2E では修正前でも通った。** フェイクの pty は後始末が一瞬で終わり、
見回りが入る隙が無い。実機は本物の pty の後始末に時間がかかる。試験では
`will-quit` で**プロセスの終了だけを 1.5 秒遅らせて**隙間を作り、Red を確かめた。
**実機でしか起きない競合は、実機の隙間を試験で作ってから直すこと。**

残る隙: 最後の周でカーソルの保存に失敗していた場合、閉じたあとに書き直す
機会が無い（以前は次の周で書き直していた）。めったに無いので見送った。

### 確かめている間に届いた行が、閉じると消えていた（形 1）

配達の確認が取れたとき `cursor = readTo` としていた。打ってから確認が
取れるまで（確定を待つ 0.5 秒＋動くのを待つ数秒）も読み進めるので、
`readTo` には**まだ打っていない行**が入っている。カーソルがそこまで飛ぶと、
**その行を打つ前に閉じたら、次の起動では二度と拾わない**。

いまは打った時点の読み位置を `Pending.endsAt` に覚え、そこまでしか進めない。

★ **思ったより起こりやすい。** 受付は便を受けると数分作業するので、その間
2 通目はずっと保留にいる。**その数分に再起動すれば消えていた**。

「状態を進めてから副作用」（形 1）の亜種: 進める量が、副作用が済んだ範囲より
大きかった。

### 届け先のエージェントが落ちたら、便が黙って溜まり続けていた

**記録を集計して偏りに気づいた。** 10/6〜10/8 の配達 23 回は全部 0.91〜0.94 秒で、
**どれも届いた瞬間に届け先が指示待ちだった**。届け先が指示待ちに戻れない場合を、
実機では一度も通っていなかった。

**実機で採った（空の一時フォルダで `claude` → 何も頼まず `/exit`）:**
claude は**自分の枠を消して** PowerShell に戻る。ペインは**待機（idle）**になり、
二度と指示待ちに戻らない。トリガーは保留するだけで、**理由はどこにも出なかった**
（ペインの「保留 N」だけ）。ペインごと終われば exited で、同じく黙っていた。

いまは保留があるときに限り、終了は**すぐ**、待機は **1 分**（`IDLE_WARN_MS`）
続いたら理由を出す。作業中・確認待ちでは出さない。

★ **先に推測した危険は外れていた。** 「最後の枠（`? for shortcuts`）が画面に残り、
指示待ちと判定されて PowerShell に打ち込まれ、エラー出力を『実行された』と
取り違えて便が消える」と組んだ画面では確かにそう判定された。**実物の claude は
枠を消すので起きない。** 組んだ画面で判定関数を回しても、それは判定関数の
試験であって、エージェントの振る舞いの証拠にはならない。**画面は実機で採る**
（#27 と同じ教訓）。

★ 採るときに見えたこと: PaneDeck のペインの中から `claude` を起動すると、
`CLAUDE_CODE_CHILD_SESSION` を引き継いで**会話の記録が保存されない**と出た
（私のセッションから起動したため）。PaneDeck 自体は人の端末から起動するので
ペインには関係しないが、**採る道具はエージェントの中から走らせると環境が違う**。

### ログの索引が消えていた —「読めなかった」を「無い」と扱う

**実機のログ置き場を数えて気づいた**（中身は開いていない）。98 個のうち
**37 個が索引に無く**、索引には **10/4 以降しか載っていなかった**。片付けは
索引に載ったものしか触らないので、8/3 のログが 30 日を過ぎても残っていた。

穴は 2 つ。**どちらも「読めなかった」を「無い」と同じに扱っていた**:

- `addToIndex`: 索引が一瞬でも読めない（書きかけ・他が掴んでいる）と
  `readIndex` は空を返し、そこへ 1 件足して**上書き** → 索引が丸ごと消える。
  しかも直接書いていたので、途中で落ちると壊れた JSON が残り、次も「空」
- `cleanupLogs`: 開けなかっただけのファイルを「消された」として**索引から落とす**

いまは `loadIndex` が「無い / 壊れている / 読めない」を見分ける。読めなければ
**書かない**、壊れていれば**退避（`.broken-<時刻>`）してから**作り直す。
索引は一時ファイルに書いてから置き換える。片付けは ENOENT のときだけ落とす。

どちらが実際に起きたかは**記録が無いので分からない**。

★ 試験で踏んだこと: 「開けなかったものは落とさない」は**修正前でも通った**。
差し込んだ stat が使われず、本物の stat が成功していただけ。**差し込んだものが
使われることを確かめる試験**を先に足して Red にした。

### 全終了は確認してから・直前の構成に戻せる（2026-10-09）

全終了は**確認なしで**全ペインを終了し、復元用の控えを空で上書きしていた。
作業中の claude も途中で止まり、**どのペインがどの会話だったか**（#33 の id）を
忘れる。押し間違い 1 回で本体と受付の会話のつながりが両方切れる。

- **A. 確認を出す**: 「N 個のセッションを終了します（作業の途中 M）」。作業中と
  確認待ちを「途中」に数える。**数を出す** —— 「本当に？」だけだと反射で押される
- **B. 直前の構成を 1 つ控える**: 全終了の**直前に** `last-session.previous.json`

  **同じ経路**（`openFromEntry`、会話の再開を含む）で戻す。戻したら控えは消す
- **自動では戻さない。** 「全部閉じたら次の起動は空のまま」は変えていない
- 1 個ずつ閉じて空になった場合は控えない（全終了だけ）

### 全体試験でだけ落ちる auto-restore（#38）— まだ原因不明

`relaunch()`（閉じてすぐ起動し直す）を通る試験が、**全体試験 4 回中 3 回**
30 秒で時間切れになった。落ちる試験は毎回違うが、**どれも relaunch を通る**。
アプリの stderr には node-pty の `AttachConsole failed` が出ている。

★ **単独で回し直す前に `test-results/` を退避すること。** 回し直すと

## 会話を指定して起動する（#33）

### 初回と再開で呼び方が違う

実測（claude 2.1.288）:

| 呼び方 | 結果 |
|---|---|
| 会話 id を指定して初回 | 新しい会話が始まる |
| 同じ id でもう一度 | **`Session ID ... is already in use.` で落ちる** |
| 再開の呼び方 | 再開し、前の内容を覚えている |

**1 つの呼び方に簡約してはいけない。** 簡約は 2 回目の起動でしか壊れないので、
気づくのが最後になる。

### `initialCommand` は人が頼んだ形のまま保つ

**打つものと、覚えておくものは別。** 会話 id を `initialCommand` に焼き付けると、
それが構成に保存され、次の復元で**再開の呼び方が使われず**、同じ会話を始める形で
起こそうとして落ちる。

`session-manager` の `create` には `command`（保存される）と `launch`（pty へ
打つ）の 2 つがある。混ぜないこと。

### 自動復元と手動の復元で同じ判断を通す

`openFromEntry()` に寄せてある。**最初は自動復元だけに置いて、手動の復元
（ダイアログから構成を選ぶ）が素通りしていた** —— 記録を調べずに再開しようとして
落ちる状態だった。E2E が見つけた。

### 記録の場所はプロファイルが持つ

`claudeRecordFile()` が組み立てる。符号化は実機から採取した形:

```
C:\app\panedeck → ~/.claude/projects/C--app-panedeck/<uuid>.jsonl
```

- **区切りは 1 文字ずつ置き換える。** `+` を付けて続きをまとめると
  `C:\app` が `C-app` になり、実機の `C--app-panedeck` と合わない（踏んだ）
- 宣言しないプロファイルは調べずに、落ちたときの退避だけに頼る

### 検証できない環境がある

エージェントのセッションの中から起動したデッキは
`⚠ Transcript saving is off — inherited CLAUDE_CODE_CHILD_SESSION marker` と
出て、**記録を残さない**。この状態では再開するものが無いので、**正しく作っても
壊れて見える**。実機で確かめるときは、人が自分で起動したデッキを使うこと。

### E2E は本物のエージェントを起こさない

`tests/e2e/resume.spec.ts` は `initialCommand: "echo"` に `agent: "claude"` を
組み合わせる。確かめたいのは**どう起こしたか**なので、起こす相手は何でもよい。
クォータも使わない。

- 実 pty なので**書き込んだ文字は覗けない**（`written` はフェイクの持ち物）。
  シェルが echo するので記録から読む
- **端末は 80 桁で折り返す。** プロンプトが長いと流し込んだコマンドの途中に
  改行が割り込むので、空白を落として比べる（踏んだ）

### ★ 端末の記録で「含まれないこと」を見てはいけない

PSReadLine は**履歴からの候補を薄い字で端末に書く**。`echo` と打った瞬間、
前に使った `echo --session-id <別の uuid>` が出力に流れ、ログに残る。

CI でこれに引っかかり、**ペインが会話を取り違えたと誤って判定した**。
製品は正しく、テストが予測変換を読んでいた。

- **「含まれること」は見てよい**（実際に打った文字は必ずある）
- **「含まれないこと」はセッションの状態で見る**（`list()` の `sessionId`）

同じ理由で、**同じディレクトリで繰り返すテストは履歴を共有する**。前のテストが
打った文字が次のテストの出力に現れうる。

  待ち受け（Monitor）は 1 度も張られなかった
- 受付のログは 1 時間半で 26 万文字。保持 30 日・上限 500MB なので支障はない

**dogfood が見つけた設計の誤り（テストは全部緑のままだった）**:

1. `❯` を「選択肢」と分類する計画 —— 実機では入力プロンプト
2. `readyPatterns` に不可視のバックスペースが入り、永久に一致しなくなっていた
3. カーソルを「読んだ位置」で進めていた —— 保留中に閉じると行が消えた
4. PowerShell の確認プロンプトがどのプロファイルでも未検出だった
5. 文面と CR を一度に書いていた（#32）—— **手で操作している限り出ない**
6. 復元で振った会話の id を保存していなかった（#33）—— **2 回目の復元で初めて壊れる**
7. 手動の復元が `resumePlan` を素通りしていた —— E2E が見つけた

**私（引き継ぎ元のセッション）の役だったもの**: Tealus の `panedeck` queue を
Monitor で待ち受けていたが、**2026-10-04 に停止した**。以後、配るのは受付 1 人
（`handle-tealus` skill、Monitor を張らない）。この規則は README にも書いた。

## トリガーは「変わっていなければ読まない」（#35）

以前は 300ms ごとに**監視ファイルを丸ごと読み直して**いた。実測:

| 監視ファイル | 旧（毎回読む） | 新（stat で飛ばす） |
|---|---|---|
| 10 KB | 0.08% | 0.005% |
| 1 MB | 0.51% | 0.005% |
| 10 MB | **3.75%** | 0.005% |

（1 コア換算・常時）。`stat` だけなので**大きさに依存しなくなった**。

★ **queue は追記だけなので、この数字は下がらない。** 実機の `tealus.jsonl` は
既に 2.4 MB ある。「全セッションを PaneDeck へ」の話と正面でぶつかる性質だった。

- バイト数の `byteSizeOf` と文字数の `sizeOf` は**別の依存**。後者は中身を読んで
  数えるので（追いかけ始める位置の決定に使う）、飛ばす判定には使えない
- 大きさが取れないときは読みにいく。**読めない理由を毎回出すため**
- **同じ大きさのまま中身が入れ替わる書き方には気づけない。** これは以前の
  「短くなったら入れ替わり」判定でも拾えていなかったので、劣化ではない

### 1 行は改行で終わって初めて 1 行（2026-10-07 に直した）

`collect()` は増えた分を `readTo = text.length` まで読んだことにして、
`/
?
/` で切った**空でない断片を全部**保留に積んでいた。

→ **書き手が 1 行を 2 回以上に分けて書き、その間に 300ms が挟まると、
1 件が「前半」「後半」の 2 件に割れて配られる。** 前半は JSON として
読めないので `{id}` が置き換わらず、`{id}` という文字がそのまま打たれる
（試験の失敗がまさにこの形で出た）。

**最後の改行より後ろは読んだことにしない**ように直した。`readTo` を
進めないのが肝で、**進めると #35（変わっていなければ読まない）と合わさって
断片が永久に捨てられる**。

★ **受付ペインが #34 の検討中に指摘した。** Tealus の queue は agent-server が
1 回で書くので踏んでいなかったが、**郵便受け（#34）で書き手が CI・スクリプト・
人の手に広がると踏みやすくなる**。「誰でも 1 行書けば届く」が売りなのだから、
割れ方の責任は受け取る側にある。

★★ **完成しない断片は黙って抱えない**（`PARTIAL_WARN_MS` = 10 秒）。
書き手が改行を書かずに止まると便は永久に届かず、#35 のおかげで読み直しも
しないので、**何も起きないまま静かに待つ**ことになる。#36 で潰したはずの
「届かない理由が見えない」形なので、猶予を過ぎたら理由としてツールバーと
記録に出す。

- **この判定は `check()` に置く。** `collect()` は大きさが変わらなければ
  先頭で戻るので、**断片のまま止まった書き手の回には入ってこない**
- 他に理由があるときは譲る（届け先が無いほうが人にとって直せる話）
- **普通に分かれて書かれた行は数百ミリ秒で完成する**ので掛からない

★ 試験で踏んだこと: 「完成したら理由が消える」の期待する出来事の並びを
`trigger-error → trigger-ok → delivery` と書いたが、正しくは
`trigger-error → typed → trigger-ok` だった。**配達は確定と確認を経てから**で、
`check()` 1 回では出ない。また**机の上で並びを決めてから実物に外された**。

### 2 段目（末尾だけ読む）は**やらないと決めた**

残る費用は「行が来たときだけ全体を読む」で、10 MB で 11 ミリ秒・1 回。数分に
1 回なら平均すれば 0.005% に埋もれる。対して危険が 3 つ:

1. カーソルは**文字数**で数えている。UTF-8 でバイト位置へ読み替えるには別の
   バイトカーソルと、**再起動時の導出**が要る
2. 境界で多バイト文字が途切れる処理
3. 「改行までしか読まない」にすると、**改行で終わらない最後の行が永久に
   届かない**（いまは届く）

**得るものが平均 0.005%、危険が 3 つ。** 測ってから決めたことなので、
必要になったら測り直すこと。

### ついでに分かった「安い」もの

同じ計測で、疑っていた 2 つは**無料だった**:

- 判定ひと巡り（画面を読む → ANSI 除去 → 正規表現）: **1 ペイン 5.9 マイクロ秒**。
  64 枚でも 300ms の予算の 0.13%
- ヘッドレス端末への書き込み（#31）: **1 KB あたり 0.7 マイクロ秒**。
  50 KB/秒 を吐くペインでも 1 コアの 0.003%

**ペイン数を増やすとき、この 2 つは気にしなくてよい。**

## ペインを増やしたときの費用（実測）

**PaneDeck 側の計算はボトルネックにならない。** 1 秒に 5 回 行を書き換える
程度のペインを並べて測った（1 コア換算 %、15 秒の窓）:

| 枚数 | 本体 | 画面(xterm) | GPU | 合計 |
|---|---|---|---|---|
| 4 | 1.7 | 1.6 | 1.9 | **5.2%** |
| 8 | 2.6 | 4.2 | 2.5 | **9.3%** |
| 16 | 5.3 | 8.2 | 4.1 | **17.6%** |

**1 枚あたり約 1.1%**、きれいに線形。16 枚で 1 コアの 17.6%（28 コアの機械で 0.6%）。

★ **効くのは枚数ではなく「エージェントがどれだけ描くか」。** 実物の claude が
入った 4 枚のデッキでは 画面だけで 15.2% だった —— 全画面の塗り替え・回転記号・
トークン数で、上の軽いペインとは桁が違う。1 枚 5〜6% と見て、20 枚で 1 コア強。

内訳の細かい方も測ってある:

- 判定ひと巡り（画面を読む → ANSI 除去 → 正規表現）: **1 ペイン 5.9 マイクロ秒**。
  64 枚でも 300ms の予算の 0.128%
- ヘッドレス端末への書き込み（#31）: **1 KB あたり 0.7 マイクロ秒**。
  64 枚が各 50 KB/秒 吐いても 1 コアの 0.088%

**枚数を増やすとき、この 2 つは気にしなくてよい。**

### では何が制約か

| 制約 | 根拠 |
|---|---|
| クォータ | アカウント側。PaneDeck では決められない |
| メモリ | claude 1 枚あたり約 0.3 GB（2 枚 = 0.59 GB の実測）。20 枚で 6 GB |
| **題の重なり** | 既定の題は作業ディレクトリ末尾。**20 枚なら重なりが常態**で、トリガーは（正しく）送らなくなる。**いまは 1 枚ずつ手で付け替えることになる** |

★ **いちばん手前にあるのは題の重なり。** 機能ではなく運用の問題だが、
「多くのセッションを制御する」に進むなら最初に当たる。

### 測っていないこと

- 実物のエージェントを 16 枚以上並べた場合（クォータを使うので未実施）
- **合成（コンポジタ）が他のアプリの入力の滑らかさに与える影響。**
  2026-10-04 に「他のアプリでタイピングが重い」という話があり、CPU と
  メモリでは説明できなかった（原因は Phone Link の背景処理 551 本だった）

## 自分のコードを読み返して出た形（2026-10-05）

今日見つけた不具合は**形が 3 つに絞れる**。新しいコードを書いたら、この 3 つで
自分を点検すること。

### 形 1: 状態を進めてから副作用

**先に印を進めると、副作用が失敗したときに二度と戻ってこない。**

| 場所 | 何が起きるか |
|---|---|
| トリガーの「見た大きさ」（#35） | 読めないファイルの理由が 300ms で消え、以後黙る |
| トリガーのカーソルの保存 | 書けなかったら二度と書き直さず、**次の起動で同じ便がもう一度届く** |

★ `log-writer` は**正しく**書けてからバッファを空けている（失敗時は報告して
止める）。ここを手本にする。

### 形 2: 変えたのに保存しない

| 場所 | 何が起きるか |
|---|---|
| 自動復元で振った会話の id（#33） | 死んだ id が残り、**起動のたびに永久に繰り返す** |
| 退避で振り直した id | 同じ。1 回では止まるが、起動をまたいで繰り返す |

★ **セッションが増減・変化したら保存**。ただし終了時の `closeAll()` では
保存しない（構成が空になる）。

### 形 3: 資源の状態を見ずに触る

| 場所 | 何が起きるか |
|---|---|
| `close()` が終了済みの pty を kill（#16 の守りが resize だけだった） | 死んだ ConPTY への操作は返ってこないことがあり、本体が固まる |
| 確認を**題で引いたペイン**で行う（#32 の抜け） | 打ったのとは別のペインの動きを見て「届いた」と判断し、**行が消える** |

★ pty を触る所（write / resize / kill）は**全部** `exited` を見る。
★ **打った相手と確かめる相手は同じでなければならない。** 題は付け替えられる
ので（#28）、題で引き直すと別のペインになりうる。

### 設定でも規則を守らせる

README の「1 つの queue に配る人は 1 人」は、**設定が同じファイルを見る
トリガーを 2 つ許していた**。カーソルは監視パスを鍵に保存するので、2 つ置くと
互いに潰し合う。サービスを名前で重複排除しているのと同じ理由で、監視パスで
重複排除するようにした。

### テストが穴を突いていないことがある

「別のペインに入れ替わったら行を戻す」のテストは、最初**入れ替えた先を
`ready` にしていたので通ってしまった** —— 確認そのものが起きていなかった。
**危ないのは入れ替わった先が作業中のとき。** 通ったときは「何を通ったのか」を
疑うこと。

## 見せるだけでは残らない（#36）

**ツールバーは「いま」を描き直す表示。** だから **直ると証拠が消え、閉じれば
全部消える**。夜中に 7 回落ちたサービスは、復帰後は「サービス 1」と出るだけ
（`serviceSummary` は「再起動中」か「停止」のときだけ回数を添える）。

★ **1 日分を分析しようとして気づいた。** 機械の数字（メモリ・ハンドル・
プロセス数）は記録係のおかげで全部あったのに、**アプリ自身の出来事だけが
無かった**。

いまは `events-YYYYMMDD.jsonl` をペインの記録と同じ場所・同じ索引に積む
（＝保持期間の片付けに乗る）。

### 設計で決めたこと

- **毎周は書かない。** 届け先が無い状態は 1 秒に 3 行生む。**理由が変わった
  ときだけ** 1 行（`trigger-error`）、消えたときも 1 行（`trigger-ok`）
- **保留は出来事にしない。** 配達の行に `waitedMs`（いちばん古い行がどれだけ
  待ったか）を入れれば、**1 行で保留の有無と長さが分かる**。状態を毎周書くより
  読みやすく、静かな日は何も増えない
- **押し直しの回数も配達の行に入れる**（`submits`）。#32 で助かったのかが分かる
- **ツールバーはこの記録を読まない。** 表示は「いま」をその場で計算するまま。
  記録は横に置くだけ（小野さんの判断）
- **記録が書けなくても配達は続ける。** `EventLog` は投げず、失敗を数えるだけ

### 日の境目はローカル時刻（2026-10-06 に直した）

`fileFor()` は **UTC で日を切っていた**。コメントには「ペインの記録と同じく
日付で分ける」と書いてあったのに、`log-writer` のほうは**ローカル時刻**で
名前を付ける。**同じフォルダに並ぶ 2 種類が、別の日で切れていた。**

JST だと `events-20261006.jsonl` が **10/6 09:00 〜 10/7 09:00** を抱える。
朝 8 時に「今日」を読もうとすると昨日の名前のファイルを開くことになり、
**「後から 1 日を読む」という #36 の目的そのものが欠ける**。

- 行の中の `at` は **UTC の ISO のまま**。瞬間は絶対で、**束ね方だけがローカル**
- `log-retention` の経過日数はミリ秒の差なので、どちらでも変わらない

★★ **CI（UTC）ではこの手の不具合は原理的に見えない。** ローカルと UTC が
一致する場所では、どちらの実装でも同じ名前が出る。**試験が緑なのは、
試験が何も見ていないから**だった。

★★ **だから `tests/unit/event-log.spec.ts` は時間帯を `Asia/Tokyo` に固定する**
（`beforeAll` で `process.env.TZ` を差し替え、`afterAll` で戻す。Node は実行中の
差し替えを反映する）。固定して初めて、どの開発機でも CI でも**同じ日の境目**を見る。

★ 元の試験は `Date.UTC(2026, 9, 6)` で時計を作り、コメントには
`// 2026-10-06 10:02:03 (JST)` と書いてあった。**書いた本人はローカルで考え、
検証は UTC でしていた。** ローカル構築（`new Date(y, mo-1, d, ...)`）に直した
とたん、既存の 2 件が落ちた —— **その 2 件は UTC を仕様として固定していた**。
時刻を扱う試験は、**どちらの単位で作った値かを式の形で見せる**こと。
